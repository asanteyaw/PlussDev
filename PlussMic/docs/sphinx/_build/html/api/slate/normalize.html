Slate::normalize¶

Back to Slate API Reference

Signature¶

Slate::normalize(UnicodeForm form = UnicodeForm::NFC) const -> Slate

What It Does¶

Applies Unicode text normalization to every cell of a Note (string) slate, choosing one of the four standard Unicode Normalization Forms via form. Requires the slate to be Note-kind.

enum class UnicodeForm {
  NFC = 0,   // Canonical Decomposition, followed by Canonical Composition
  NFD = 1,   // Canonical Decomposition
  NFKC = 2,  // Compatibility Decomposition, followed by Canonical Composition
  NFKD = 3,  // Compatibility Decomposition
};

Normalization matters for text that might contain the same visible character represented in more than one way — most commonly, a precomposed accented letter (é as a single codepoint) versus a base letter plus a combining mark (e + a combining acute accent, two codepoints that render identically). Two byte-for-byte-different strings can look identical and still compare unequal with a plain eq(); running both through the same normalization form first makes such comparisons consistent.

Important

Requires the optional Unicode backend (GNU libunistring) for anything beyond plain ASCII normalize()’s real behavior depends entirely on whether this build links libunistring:

  • With the backend: all four forms are fully implemented via the standard uninorm_normalize routine, correctly handling precomposed and decomposed Unicode text.

  • Without the backend: normalize() still accepts pure-ASCII input — and, since plain ASCII has no combining marks, ligatures, or compatibility characters to normalize in the first place, every form behaves as an identity transform and returns the input unchanged (see Example 1). But any non-ASCII input throws "Note::normalize: non-ASCII text requires a Unicode backend" — there is no partial or best-effort fallback for non-ASCII text.

Confirm this build’s Unicode support before relying on normalize() for any text that might contain non-ASCII characters.

Parameters¶

form (UnicodeForm, default UnicodeForm::NFC) Which normalization form to apply: NFC, NFD, NFKC, or NFKD.

Returns¶

Slate A new Note-kind slate, same length as *this, holding the normalized text.

Examples¶

Example 1. Plain ASCII text under the default form (NFC) — a no-op, since ASCII has nothing to normalize, and this behavior holds regardless of whether this build links the Unicode backend.

using namespace pluss::table;

auto titles = Slate(pluss::make_note({"Hello World", "ASCII text only", "x"}),
    pluss::make_series(std::vector<bool>{true, true, false}));
std::cout << titles;

auto out1 = titles.normalize();
std::cout << out1;

Output (before, identical to output after)¶

0  Hello World
1  ASCII text only
2  NULL

ptype: Note

The output is byte-for-byte identical to the input: NFC (like every other form, on ASCII) has nothing to canonicalize when there are no combining marks or compatibility characters present. The invalid third row stays NULL.

Example 2. Explicitly requesting each of the four forms on the same ASCII input — all four produce the identical result, since the distinctions between NFC/NFD/NFKC/NFKD only matter for text containing decomposable or compatibility characters, none of which plain ASCII has.

auto nfc = titles.normalize(UnicodeForm::NFC);
auto nfd = titles.normalize(UnicodeForm::NFD);
auto nfkc = titles.normalize(UnicodeForm::NFKC);
auto nfkd = titles.normalize(UnicodeForm::NFKD);
// nfc, nfd, nfkc, and nfkd are all identical to titles here.

Example 3. Non-ASCII input without the Unicode backend throws — shown here as the documented failure mode rather than a specific transformed value, since the exact behavior depends on this build’s optional dependency (see the important callout above).

auto accented = Slate(pluss::make_note({"caf\xC3\xA9"}));  // "café"

try {
  auto out3 = accented.normalize();
} catch (const std::exception& e) {
  std::cout << e.what();
}

Output (build without the Unicode backend)¶

Note::normalize: non-ASCII text requires a Unicode backend

A build with libunistring linked would instead perform genuine Unicode normalization on this input rather than throwing — but the exact byte-level output in that case isn’t asserted here, since it depends on a build-time optional dependency rather than anything guaranteed by the public API alone.

Example 4. A non-Note slate throws.

auto numbers = Slate(pluss::make_series({1.0, 2.0, 3.0}));
try {
  auto bad = numbers.normalize();
} catch (const std::exception& e) {
  std::string msg(e.what());
  std::cout << msg.substr(0, msg.find('\n')) << "\n";
}

Output¶

Slate::normalize: expected Note payload

Notes¶

  • Requires the calling slate to be Note-kind.

  • All four UnicodeForm values are identity transforms on pure ASCII text, with or without the Unicode backend.

  • Non-ASCII input throws outright when this build lacks libunistring — there is no partial fallback. See the important callout above.

  • A null cell on input stays null on output.
