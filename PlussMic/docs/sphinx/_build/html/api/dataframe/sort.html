DataFrame::sort¶

Back to DataFrame API Reference

Signature¶

DataFrameSortBuilder DataFrame::sort(bool ascending = true, bool nulls_last = true) const

What It Does¶

The entry point into the frame’s reusable sort-planning workflow. sort() binds the current frame — along with the default direction and null placement every subsequently-added key inherits unless overridden — and hands back a DataFrameSortBuilder.

With several keys, the eventual plan is lexicographic / tuple-based: the first key is primary, the next key breaks ties within equal first-key values, the next breaks remaining ties, and so on.

Mental Model¶

There are four separate ideas on this surface:

  1. Builder defaults

  • ascending

  • nulls_last

These are inherited by plain key-name overloads unless a key later overrides them.

  1. The key plan

  • by(...) starts or replaces it

  • then(...) appends tie-break keys

  1. The active key

  • asc(), desc(), nulls_first(), nulls_last() mutate only the most recently added key

  1. Optional partitioning

  • within(...) says rows may only move inside groups, not across them

That is why the builder exists: it separates defaults, key declaration, key-local refinement, and execution.

When To Use It¶

Use sort() instead of arrange() when:

  • you want to build the key plan step by step

  • different keys need different direction or null placement

  • you want to reuse the same permutation via order()

  • you want partitioned sorting with within(...)

Use arrange() when:

  • the full sort spec is already known up front

  • you just want one direct execute-now sort call

Use the DataFrameSortBuilder API Reference for the builder workflow itself:

  • plan keys with by(), then(), and within()

  • refine the active key with asc(), desc(), nulls_first(), and nulls_last()

  • materialize with order(), yield(), head(), and tail()

Important

sort() alone plans nothing — no key is set until by() sort() only records the default direction/null-placement and binds the frame; calling a terminal (yield()/order()/head()/tail()) before any .by(...) throws — see DataFrameSortBuilder::by’s own edge-case example.

Important

Validation is lazy — unknown feature names surface at the terminal, not at by()/then() .by("nope") itself never checks whether "nope" exists on the frame — the unknown-feature throw only fires when a terminal method (yield()/order()/head()/tail()) actually executes the plan. You can chain several .by(...)/.then(...) calls referencing features that don’t exist yet without any of them throwing, right up until you call a terminal.

Parameters¶

ascending (bool, default true) The default sort direction every key added via .by(...)/.then(...) inherits, unless that key overrides it (e.g. via an ArrangeSpec, or a later .desc() call).

nulls_last (bool, default true) The default null placement every key inherits, unless overridden.

Returns¶

DataFrameSortBuilder A binder for the current frame — call .by(...) to start planning value keys, .within(...) to partition into groups first, then a terminal method to execute.

Failure Modes¶

  • calling a terminal with no sort keys planned -> validation error

  • calling then(...) before by(...) -> validation error

  • calling asc() / desc() / nulls_first() / nulls_last() before any key exists -> validation error

  • unknown feature names -> typically validation error only when a terminal executes

  • negative n for head() / tail() -> validation error

Examples¶

Example 1. The simplest plan: one key, default ascending direction, executed with .yield().

using namespace pluss::table;

auto df = DataFrame({
    {"city",  Slate(pluss::make_note({"Tema", "Accra", "Accra", "Tema"}))},
    {"sales", Slate(pluss::make_series({120.0, 100.0, 90.0, 200.0}))},
});

auto out = df.sort().by("sales").yield();
std::cout << out;

Output¶

===================
     | city   sales
-------------------
2    | Accra  90   
1    | Accra  100  
0    | Tema   120  
3    | Tema   200  
-------------------
[4 cs x 2 feat]

Example 2 (edge case). Pass ascending = false to sort() itself to change the default every subsequently-planned key inherits, rather than calling .desc() afterward.

auto out2 = df.sort(false).by("sales").yield();
std::cout << out2;

Output¶

===================
     | city   sales
-------------------
3    | Tema   200  
0    | Tema   120  
1    | Accra  100  
2    | Accra  90   
-------------------
[4 cs x 2 feat]

Example 3. Several plain feature names all inherit the same builder default.

auto out3 = df.sort(false).by({"city", "sales"}).yield();
std::cout << out3;

Output¶

===================
     | city   sales
-------------------
3    | Tema   200  
0    | Tema   120  
1    | Accra  100  
2    | Accra  90   
-------------------
[4 cs x 2 feat]

Both keys inherit ascending = false, so city sorts descending first and sales breaks ties descending inside each city.

Example 4. Use ArrangeSpecs when different keys need different directions.

auto out4 = df.sort().by({
    DataFrame::ArrangeSpec{"city", true, true},
    DataFrame::ArrangeSpec{"sales", false, true},
}).yield();
std::cout << out4;

Output¶

===================
     | city   sales
-------------------
1    | Accra  100  
2    | Accra  90   
3    | Tema   200  
0    | Tema   120  
-------------------
[4 cs x 2 feat]

Now city is ascending but sales is descending inside each city. This is the builder equivalent of a per-level ascending=[...] style API.

Notes¶

  • See the important callouts above — sort() alone plans nothing, and feature-name validation is deferred to the terminal call.

  • ascending/nulls_last set the builder’s defaults; any per-key override (an explicit .asc()/.desc()/.nulls_first()/.nulls_last() call, or an ArrangeSpec with its own fields set) wins for that key specifically.

  • Plain .by({"a", "b", "c"}) uses one shared default for all three keys. Mixed per-key directions require ArrangeSpecs or post-by(...) mutation of the active key.

  • With plain key-name overloads, sort(false).by({"age", "salary", "score"}) means all three keys are descending. It is not the pandas-style ascending=[...] case until you move to ArrangeSpecs or active-key mutation.

  • Not noexcept; sort() itself does no validation work — every check is deferred to the terminal.
