### Doctrine for MATLAB Inspiration
Loops(and nested loops) only when inevitable or needed for correctness. Linear passes preferred otherwise vectorized Series/Note/Timeline ops where possible. Modernized cpp 20 semantics, when loops are needed and stl iterators and algos (they are not necessarily faster than classical loops but are cleaner and more compact) can do it, then they can be used rather than classical loops, other times you might seek clarity so you can use traditional loops(they are more verbose but easier to understand), so you should manage it. Smart and vectorized delegations. No aliasing/unnecessary bloat. Prefer enum-based to string based configs, you may use struct based with enum based when there are multiple setting. For example SomeOptions ops; ops.some_setting= some_enum_selection, ops.some_other_settings = some_other_enum_selection, etc. Avoid naming like 'MATLAB' or anything that gives us off as 'copied from MATLAB', also avoid method/function names given in the MATLAB implementation in favor of your own concise but descriptive naming to make it feel pluss native. Keep reading relevant files in the MATLAB reference folder for all your implementations so you don't write degenerate code. Don't copy it over verbatim, just be inspired by it while you implement your own. When you encounter .p files, infer from their behaviour or call sites. Modularize your code, feel free to create new files and folders and manage the folder structures professionally in a way that is scalable and maintainable. Keep all implementations platform-agnostic so it runs on the platform of the input Series(i.e don't forcibly put Series on CPU(using .to(pCPU)) or call .item<double>, .to_vec<double>, .to_host<double>, etc, as these methods will materialize on CPU first and destroy platform consistency), just use Series ops so we stay on the same platform as input Series. So when a user supply a Series input that is on GPU(e.g MPS), then your implementation's computations will stay on GPU throughout (unless you INEVITABLY need to fallback on CPU and get back on GPU again. This may reduce performance or introduce memory overhead so it is discouraged but not stricly prohibited. If you rely purely on Series ops, you wouldn't need to worry about platform issues because it will compute on the platform of the user supplied input). So basically, we are letting the user determine what platform their computations should run on. Memory issues and platform inconsistency issues are already handled by the Series platform utilities. The end goal for our users is first and foremost accuracy, then performance, then ease-of-use(i.e no verbose typing: "write small code, achieve a lot").
