# `nn::module` Introduction

## What This Category Owns

`module` owns the one base contract every layer, container, and composed
network in `nn` implements, and the one container that composes them:

- [`Module`](Module.md) — the base class: parameter/buffer/child-module
  registration, `train`/`eval` mode, `to(platform/dtype)` moves,
  `parameters`/`buffers`/`modules` (flat and named, recursive through
  children), and `snapshot`/`restore` for checkpointing.
- [`Schedule`](Schedule.md) — a named, ordered composition of modules and
  callables run in sequence. Every multi-layer network in this reference is
  built by chaining layers into a `Schedule`.

## The `ModuleHolder` Indirection

Every concrete layer type elsewhere in this reference (`Fusion`, `Conv1d`,
`RNN`, `MultiheadAttention`, `Schedule` itself, ...) is a thin value-type
wrapper around a `shared_ptr` to the real `Module` subclass. The pattern is
generated by a macro:

The public layer value holds the implementation and forwards its operations. You use
the layer value directly; its implementation type stays behind that interface.

`ModuleHolder<Impl>` forwards `train`/`eval`/`to`/`forward`/`operator()`/
`parameters`/`named_parameters`/`buffers`/`named_buffers`/`modules`/
`named_modules`/`snapshot`/`restore` through `operator->`, so calling
`layer.forward(x)` or `layer(x)` on `Fusion` reaches `FusionImpl`'s own
`forward` without you ever naming `FusionImpl` or a `shared_ptr`. Three
practical consequences:

- A layer value is default-constructible into an **empty** state
  (`Fusion f;` if `Fusion`'s constructor is called with no args that build a
  real `FusionImpl` -- most layers require constructor arguments, so check
  each type's own page) or explicitly empty via `nullptr`
  (`Fusion f(nullptr);`) — calling any forwarded method on an empty holder
  throws (`ModuleHolder: attempted to access an empty holder`).
- Copying a layer value copies a `shared_ptr` — both copies share the same
  underlying weights. Use `.clone()`-style deep copies (built per-layer where
  offered) when you need independent weights.
- Registering a layer as a child of another `Module` (`module_record`) works
  transparently whether you pass a bare `Module&` or a `ModuleHolder`-wrapped
  layer — `Module::module_record`'s template resolves either shape.

## Registration Discipline

Concrete `Module` subclasses register their learnable state through two
`protected` methods, both by convention called from the constructor and never
after: `parameter_record(name, series)` (gradient-tracked, requires an
already-*defined* `Series`) and `buffer_record(name, series)`
(not gradient-tracked — running statistics, position tables, anything that
travels with the module but is not learned). Both require allocating the
`Series`' real storage first (`Series::empty(shape, dtype, platform)`),
registering it once, then filling values afterward with an in-place op
(`.copy_()`, `.uniform_()`) inside a `reset_parameters()`-style method —
reassigning the member (`weight_ = uniform_(...)`) instead of mutating it in
place silently untracks an already-registered parameter.
